# Laundry Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans for each assigned work package, or superpowers:subagent-driven-development when parallel execution is explicitly authorized. Follow the ownership and dependency rules below. Checkboxes track implementation; this document does not claim code is built.

**Goal:** Deliver customer and delivery-partner apps with eCommerce service ordering, reliable garment custody, third-party logistics and WhatsApp voice-note booking.

**Architecture:** One TypeScript monorepo, one modular backend, one PostgreSQL database and a durable background worker. All channels use the same order engine. Separate module ownership enables concurrent work without separate microservices.

**Tech stack proposal:** React Native + Expo development builds for the two mobile apps; Next.js for the internal console; NestJS REST API; PostgreSQL + SQL migrations; Redis/BullMQ for jobs; S3-compatible private storage plus public catalog CDN; Razorpay hosted checkout; Meta WhatsApp Cloud API or an approved BSP. Provider adapters keep logistics and speech vendors replaceable. Exact compatible versions are pinned by A0 before other agents start.

**Spec:** [Product behavior](../../specs/product-spec.md). **Contracts:** [Shared boundary specification](../../specs/contracts.md). **Execution packets:** [Agent index](../../agent-tasks/README.md).

## Global constraints

- Two separately installed mobile apps and a restricted internal web console; Android and iOS customer support, Android-first partner device validation with iOS build compatibility.
- All order/price/capacity mutations run server-side. Clients and AI never update database tables directly.
- Money uses integer minor units and a currency field; default fixtures use INR. UTC instants plus IANA timezone; default Asia/Kolkata.
- One facility per order, multiple service lines, one consolidated return. Two logistics legs. No subscription, COD, wallet, split return or live voice calls in v1.
- No production secrets, customer data or real charges in developer fixtures. Images and reviews are traceable to consent/licensing.
- Backend verifies ownership and role on every request; operators cannot bypass audit logging.
- Shared contracts are versioned. No agent edits outside its allowlist, root manifests, lockfile or migrations without coordinator assignment.

## Architecture and ownership

```text
Customer app ───────┐
Partner app ────────┼─ authenticated REST ── API composition root
Operations web ────┤                           │
WhatsApp webhook ──┘                    Order orchestration
                                              │
                         Catalog · Billing · Logistics · Fulfillment
                                              │
                          PostgreSQL + transactional outbox
                                              │
                               Worker → external adapters
                       WhatsApp · payment · logistics · transcription
```

This is a modular monolith: modules share a deployment/database, but own their tables and exposed commands. No cross-module SQL writes. Strongly consistent order transitions use a database transaction; provider calls happen after commit through a durable outbox. Queue delivery is at least once; each consumer deduplicates. Redis loss must not erase committed work: the database outbox is replayable.

**Why this stack:** shared TypeScript reduces translation between mobile, API and contracts. Expo development builds support native integrations; native library changes require rebuilding the client ([Expo](https://docs.expo.dev/develop/development-builds/use-development-builds/)). Nest modules provide explicit boundaries ([Nest modules](https://docs.nestjs.com/modules)); BullMQ integration supplies persisted background jobs ([Nest queues](https://docs.nestjs.com/techniques/queues)). PostgreSQL transactions and locks protect capacity/order changes ([PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html)). These are design choices, not a claim that any vendor is already configured.

### Parallel execution protocol

One branch/worktree per active worker, all based on the same contract baseline. Each worker reads the product spec, contract file and its packet. A worker may read other modules but cannot modify them. New dependencies, migration changes or API changes go to A0 as a written request containing consumers, schema diff and tests; keep the affected task pending instead of silently inventing a local shape. A0 publishes additive changes to all consumers before merging them. Breaking changes require a new coordinated contract version.

Each worker returns commit IDs, exact changed paths, test commands/results, environment assumptions and remaining integration needs. The coordinator checks allowlists, reviews diffs, integrates migrations serially and merges one branch at a time. A later agent does not overwrite another agent’s uncommitted work. Initial release can use one reviewed PR per packet (10 planned logical changes); A0 may have separate foundation and final-wiring commits. Do not treat this as authorization to publish PRs or deploy.

## Service, payment and delivery rules

Service timing is calculated from facility hours, service duration, booked capacity, transport availability and buffer. A customer's deadline is a request until the quote contains a feasible promised window. Capacity is reserved transactionally for a short checkout hold (proposal: 10 minutes). Expired holds release automatically. Provider transport estimates do not replace the laundry processing duration.

Quote stores a versioned rate-card snapshot, individual quantities/weight assumptions, tax and fees, pickup/return windows, expiry and whether the price is provisional. Booking consumes a quote once. Before pickup, the customer pays the quoted amount using hosted checkout. On measured intake, any higher price requires approval and a separate top-up; any lower price creates a refund obligation. Care cannot start while an increase is unapproved or unpaid. No silent charge or automatic change of service.

Payment status is independent from order status. Verify signatures and deduplicate payment events; handle out-of-order delivery ([Razorpay webhook guidance](https://razorpay.com/docs/webhooks/validate-test/)). A browser/app success redirect is not proof of capture. If payment arrives after hold expiry, recheck capacity; confirm only if the original promise still works, otherwise flag resolution/refund and notify the customer. Never take a new slot and silently change the date.

A logistics provider adapter exposes capability checks, quote/book/cancel/status, and optionally webhook tracking. Delhivery publishes intracity ordering and a developer portal, but that does not establish access to a laundry-ready real-time dispatch API or coverage for this account ([intracity orders](https://help.delhivery.com/docs/direct-intracity-orders), [developer portal](https://help.delhivery.com/home/docs/client-developer-portal-1)). A4 first builds a simulator and manual dispatch adapter, then connects a contracted provider using its supplied documentation. Test both customer → facility and facility → customer routes. Never infer a pickup from a return-delivery event.

## WhatsApp implementation sequence

1. Receive a signed webhook, persist its external message ID once, acknowledge promptly and enqueue processing.
2. Retrieve media server-side using the authenticated provider media interface, enforce size/duration/MIME limits, transcribe through `SpeechPort`, delete temporary audio after the configured retention window.
3. Parse strict `BookingDraft` fields; reject unknown service IDs and impossible quantities. Resolve dates against receipt time/timezone. Ask for missing garment types, address or deadlines.
4. Call catalog/quote tools. Present a complete editable summary including absolute dates, provisional price and promised return window.
5. Bind confirmation to the current draft revision and quote. Call the same `createCheckout` command as the app. Send hosted payment link; record payment status through verified billing events.
6. Confirm only after the order engine accepts payment/capacity. Send tracking and intake-change requests using the same order ID visible in the app.
7. Support opt-out and human handoff. Outside the 24-hour response window, send only approved templates; template rejection leaves a retry/escalation item, not a falsely “sent” notification ([WhatsApp policy](https://whatsappbusiness.com/policy/)).

Proposed voice acceptance: a consented evaluation set covering at least 30 English/Hindi/Hinglish recordings with noise, corrections and relative dates; zero unconfirmed bookings, 100% schema-valid tool calls and at least 90% exact critical-field extraction on clear in-scope recordings. Ambiguous recordings pass only when the assistant clarifies. These are launch targets to test, not measured accuracy.

## Review focus and failure tests

- **Concurrent slot and payment races:** A2/A3 test two customers taking the last slot, duplicate captures, expiry during payment and capture after cancellation. Exactly one confirmed reservation, no duplicate order and a tracked refund obligation where required.
- **Changing clothes and prices:** A2/A5/A8 test count mismatch, revised draft/quote, decline, lower final price and unpaid top-up. Old confirmation cannot authorize new terms.
- **Delivery uncertainty:** A4/A6 test booking timeout with unknown provider result, out-of-order events, canceled rider assignment, offline upload and missing bag. Never dispatch a second rider until unknown first outcome is reconciled or manually resolved.
- **Identity and privacy:** A0/A7/A8 test cross-customer order IDs, facility/rider scope, expired proof URLs, webhook forgery and attempts to link another account. Unauthorized access is denied without leaking existence or addresses.
- **Interrupted channels:** A5/A8/A9 test app killed during checkout, duplicate WhatsApp audio, transcript errors, template rejection and notification outage. Customer can resume from authoritative order state; no repeated charge/order.

## Acceptance and release gates

- [ ] Unit and module integration tests pass against real local Postgres; mock only external providers.
- [ ] Generated SDK and server pass the same schema tests. `pnpm check`, `pnpm test:contracts`, `pnpm test:integration` and `pnpm test:e2e` exist from A0 and pass on the integrated branch. Test scripts fail if expected suites are missing.
- [ ] Customer Android and iOS builds plus partner Android device flow exercise camera, permissions, deep links and payment return. Partner iOS compiles; validate on device before an iOS partner release.
- [ ] Operator completes intake adjustment, care, QC, return and support in the web console. Verified review appears only after delivery.
- [ ] WhatsApp sandbox receives an actual voice note, correctly dates it, asks missing fields and creates the same order visible in the customer app. Real call support is not claimed.
- [ ] Provider sandbox/contract test covers duplicate events, unknown booking outcome, both logistics legs, cancellation and failure. If only manual dispatch is available, production advertises operator-managed tracking and requires staffed operations.
- [ ] Payment sandbox covers capture, pending, failure, duplicate/out-of-order webhooks, top-up and refund. Reconcile captures against orders and refunds against their obligations.
- [ ] Target API p95 under 500ms for catalog/order reads at a documented pilot load of 50 concurrent sessions, excluding external provider latency. Webhook persistence/ack p95 under 2 seconds. Measure on named hardware; these are targets, not claims.
- [ ] Retry queues, dead-letter inspection, trace IDs, alerts for aging paid-but-unconfirmed orders, backup restore and audio deletion are exercised. Poll tracking every 15 seconds only while visible; back off when backgrounded/offline.
- [ ] Production deployment uses separate credentials/database/buckets from staging, approved rate cards/service areas and audited operator access. Migration rollout is additive first; retain previous API/image for rollback and never roll back by deleting live orders.
- [ ] Complete one controlled physical pilot with a real garment bag before general launch. App-store submissions, provider purchase and production deployment require explicit authorization.
