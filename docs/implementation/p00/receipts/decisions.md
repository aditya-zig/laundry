# P00 integration decisions

Every decision below was taken by the coordinator while consolidating the three pinned source branches. The decision owner is the coordinator unless the text says otherwise.

## D-01 Integration base

**Decision.** The integration branch starts from the main checkout commit `39eaa8d0d380f780886c06d44f91fb0760b3ae0c` plus the three documentation commits that carry the production plan (`7732f0c`, `c906daf`, `f477671`).

**Reason.** The plan documents must be present on the integration branch because every worker reads them before editing. Those commits touch only `docs/implementation/production-application/`, so the source tree at the integration base is byte-identical to the pinned main checkout.

**Evidence.** `git diff --name-status 39eaa8d f477671` lists only files under `docs/implementation/production-application/`.

## D-02 Canonical namespace

**Decision.** `@laundry/*` is the only active workspace namespace. Imported code is rewritten from `@wandary/*` to `@laundry/*`, and the `WandaryClient` type is renamed to `LaundryClient`.

**Reason.** The main checkout is the newest coherent source and the plan requires one canonical namespace for the SDK boundary. Importing the legacy namespace would fork the contract surface.

**Scope.** The rewrite touches imported active source, package manifests, TypeScript path mappings, Vite aliases, workflow files and tooling scripts. It does not touch historical documents.

**Evidence.** `! git grep -n '@wandary\|Wandary' -- apps modules packages tools .github` passes on the integrated tree.

## D-03 Production database guard

**Decision.** `apps/api/src/main.ts` keeps the main checkout's `laundry_dev_only` production guard and the backend branch's `127.0.0.1` and `HOST` additions. The `wandary` alternative is dropped.

**Reason.** The project has one namespace, so one guard naming one development credential is correct. The backend branch's stricter loopback check and `HOST` bind are kept because they narrow what a production start accepts.

## D-04 Route ownership

**Decision.** The four customer routes are owned by `apps/customer/app/(tabs)/`. The flat `app/index.tsx`, `app/orders.tsx`, `app/account.tsx` and `app/help.tsx` are removed.

**Reason.** A URL may have one implementation. The grouped screens are the redesign of record and the tab bar is the single navigation owner.

**Parity.** `account`, `help` and `orders` are byte-identical to the flat versions apart from the relative import depth. The flat `index` rendered a service-area check, an editable address field, a demo sign-in, a service list and links to the other three screens. The grouped owner keeps the service-area check, the demo session, the service list and the navigation, and the editable address moved to `apps/customer/app/checkout.tsx`, which lists and creates owned addresses.

**Evidence.** `git diff` between the flat and grouped screens, recorded in the consolidation document.

## D-05 API composition

**Decision.** `apps/api/src/app.module.ts` keeps every base controller and adds `PilotController`.

**Reason.** The pilot controller is a new route family. It does not replace or shadow an existing route.

**Evidence.** The merged file contains `controllers: [MiscController, AuthController, CatalogController, OrdersController, OpsController, PartnerController, BillingController, ConversationController, PilotController]`.

## D-06 Root manifest merge

**Decision.** The root `package.json` keeps the `laundry` name and the `@laundry/*` filters. The backend scripts `agents:plan`, `agents:tooling`, `cloud:doctor`, `cloud:packet`, `cloud:submit`, `test:tooling`, `verify:browser` and `verify:evidence` are added, with `@playwright/test` added as a dev dependency.

**Reason.** The backend root manifest is the pre-rename version. Importing it would revert the package identity, the filter names and the pinned-version block.

**Evidence.** The lockfile was regenerated with `pnpm install --lockfile-only` and installs with `pnpm install --frozen-lockfile`.

## D-07 Lockfile

**Decision.** The lockfile is regenerated by pnpm rather than taken from either source branch.

**Reason.** Both source branches carry a lockfile that records the legacy namespace. A regenerated lockfile matches the merged manifests exactly.

## D-08 Persistence authority

**Decision.** PostgreSQL is the canonical store for the operational domain. Convex stays in the repository for historical access and controlled migration.

**Reason.** The architecture specifies PostgreSQL, a durable worker, shared modules and canonical SQL migrations. Keeping Convex readable while it is migrated avoids a second source of truth while it is drained.

**Open item.** No live deployment was inspected during P00. Whether any hosted environment currently treats Convex as authoritative is unverified, and the migration inventory in the consolidation document is the first step to answering it.

## D-09 Historical documents

**Decision.** `docs/discovery/` and `docs/plans/laundry-app/` keep their original project name. The naming test exempts both prefixes.

**Reason.** The founder discovery record is protected source material and the planning record predates the rename. Rewriting either would falsify the record. The naming test exists to keep active source and current runbooks on one name, which this exemption preserves.

**Evidence.** `packages/contracts/test/project-naming.test.ts` carries the exemption with an inline reason.

## D-10 Deployment gate

**Decision.** The production deploy job in `.github/workflows/ci.yml` is unchanged. It runs only when the pushed ref is exactly `refs/heads/build/laundry`.

**Reason.** A task branch is named `cloud/<task-id>-<short-name>` and can never match that ref, so a task push cannot deploy. The newly imported `agent-verification.yml` runs checks, Playwright journeys and artifact uploads, and contains no deployment step.

**Open item.** The `build/laundry` branch still deploys on push. P01 decides whether promotion moves to an explicit authorization step.
